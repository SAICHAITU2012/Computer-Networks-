Why DNS?

DNS (Domain Name System) translates human-readable names (google.com) into IP addresses (142.250.195.46). Why not use IPs directly?

  • Memory: names beat dotted quads (especially IPv6 monsters)
  • Stability: servers change IPs; the name stays constant
  • Scaling: one name → many IPs (load balancing) · many users → nearest IP (CDN geo-routing)
Analogy
DNS = the Internet's phone book: you know the name ("Mom"), the phone book gives the number. And like a good contact app, everyone caches recently-dialled numbers so the book isn't opened every time.

Full Resolution — Step by Step

Query: browser needs the IP for www.google.com

1Browser cache
Fresh cached answer? Use it. Done — no network.
2OS cache + /etc/hosts
Local system-level cache and hosts file.
3Ask the recursive resolver
Query to configured DNS (router, ISP, 8.8.8.8) — UDP port 53.
4Resolver cache
Cached & TTL-valid? Instant answer. Else start walking.
5Resolver → ROOT server
Root: "Not me — the .com TLD is at 192.5.6.30." (referral)
6Resolver → .com TLD
TLD: "Ask Google's nameservers — ns1.google.com." (referral)
7Resolver → authoritative
ns1: "www.google.com = 142.250.195.46, TTL 300" (answer)
8–9Cache + return
Resolver caches for TTL seconds and returns the IP; browser connects to it.
Exam
Iterative vs recursive: the resolver does iterative walks (ask root, then TLD, then auth); your machine makes one recursive request ("get me the answer, however many steps it takes"). Draw the 9 arrows — it's a guaranteed diagram question.

Caching & TTL

  • Every record carries a TTL (seconds to cache); after expiry the resolver must re-ask.
  • Low TTL = fast changes, more queries · High TTL = fewer queries, slow propagation.

HTTP — Request & Response

HTTP is text-based (human-readable), stateless (each request is independent), and request-response (client initiates, server responds).

http requestclient → server
GET /products?id=42 HTTP/1.1 ← request line Host: www.example.com ← required in 1.1 User-Agent: Mozilla/5.0 Accept: text/html Cookie: session=abc123 ← blank line { json body — POST/PUT only }
http responseserver → client
HTTP/1.1 200 OK ← status line Content-Type: text/html; charset=UTF-8 Content-Length: 4523 Set-Cookie: session=abc; HttpOnly; Secure Cache-Control: max-age=3600 ← blank line <!DOCTYPE html> <html>… ← body

Definitions + REST pattern
Idempotent = repeating gives the same result as once. Safe = changes nothing. REST: GET /api/users list · POST /api/users create · GET /api/users/42 one · PUT /api/users/42 replace · PATCH partial · DELETE remove.

Status codes

301 vs 302
permanent (browsers & SEO update) vs temporary redirect.
401 vs 403
401 "who are you?" (not authenticated) vs 403 "I know you — still no" (not authorized).
500 vs 502
this server broke vs the upstream server sent garbage (gateway view).

Cookies & Sessions — Memory for a Stateless Protocol

HTTP forgets you between requests. Cookies fix it: the server hands the browser a token; the browser returns it on every subsequent request — the server recognises the token and "remembers".

1 Login POST→2 Set-Cookie: session=abc→3 Browser stores→4 Cookie: session=abc (every request)→5 Server maps id → your session
AttributeEffect
HttpOnlyJavaScript can't read the cookie → blunts XSS token theft
SecureSent over HTTPS only → no plaintext interception
SameSite=StrictNever sent on cross-site requests → CSRF defence
Max-Age=NExpires after N seconds
Domain=.example.comShared across all subdomains
Cookie (client-side)Session (server-side)

ContainsSession ID (or data)The actual user data
Size~4 KBUnlimited
Visible to user?YesNo
Exam
Authentication vs Authorization: authN = proving identity (login, 401 when missing); authZ = checking permission (403 when denied). And: servers store a session ID in the cookie — not your data — so a stolen cookie is a stolen identity but a leaked DB row doesn't leak sessions.
