The Method — Climb the OSI Ladder

L1 Physical cable in? Wi-Fi associated? LEDs on? L2 Data Link interface up? link light? switch port active? L3 Network IP configured? ping gateway? ping 8.8.8.8? L4 Transport port open? firewall blocking? service listening? L7 Application service responding? config right? logs clean?
Figure 1. Don't guess — climb. Each rung eliminates a whole class of causes.
the 6-command checklistterminal
1 ip addr — interface up? has IP? 2 ping <gateway> — local network OK? 3 ping 8.8.8.8 — Internet routing OK? 4 ping <hostname> — DNS OK? 5 ss -tulpn | grep <port> — service listening? 6 curl http://localhost:<port> — service responding?

traceroute — Where Does It Hurt?

Sends packets with TTL = 1, 2, 3… Each router that kills a packet replies ICMP Time Exceeded — revealing itself. (Windows: tracert; better: mtr = traceroute + continuous stats.)

traceroute google.com   ·   traceroute -T -p 80 google.com (TCP, dodges ICMP blocks)
1 192.168.1.1 1.0 ms ← your gateway 2 10.50.0.1 8.2 ms ← ISP first hop 3 * * * ← ICMP filtered (traffic still flows!) 4 10.60.100.2 15.1 ms 5 72.14.239.45 18.4 ms ← Google peering 6 142.250.195.46 19.9 ms ← destination ✓
Reading it
Latency jumps locate congestion: hop4 at 200 ms after hop3 at 8 ms → the slow link is at hop 4. And * * * does not mean broken — many routers just rate-limit ICMP replies while happily forwarding your traffic.

ss / netstat — Who Is Listening?

ss — the modern netstatterminal
ss -tulpn — TCP+UDP, listening, processes, numeric — THE command ss -t state established — active connections only ss -t dst :443 — filter by destination port
Netid State Recv-Q Send-Q Local Address:Port Peer Address:Port Process tcp LISTEN 0 128 0.0.0.0:22 0.0.0.0:* sshd tcp LISTEN 0 10 0.0.0.0:8080 0.0.0.0:* python3 tcp ESTAB 0 0 192.168.1.5:52341 142.250.195.46:80 curl udp UNCONN 0 0 0.0.0.0:53 0.0.0.0:* dnsmasq
Key fields
0.0.0.0:port = listening on ALL interfaces · 127.0.0.1:port = localhost only — the #1 "works locally, dead externally" cause! · Recv-Q > 0 = app not reading its data.
TCP states that tell stories
CLOSE_WAIT pile-up → app never calls close() (bug!). Many TIME_WAIT → connection churn; enable keep-alive. Stuck SYN_SENT → destination down / firewall dropping SYN.

Answer Key
A1. b — IP works, name resolution doesn't.
A2. b — routers may rate-limit ICMP; forwarding continues.
A3. b — loopback bind accepts local connections only.
A4. b — remote closed, app never called close().
A5. b — authoritative "no such name".
A6. a — port 53 = DNS; -n disables reverse lookups.
A7. L1→L7 ladder; ip addr → ping GW → ping 8.8.8.8 → ping name → ss -tulpn → curl localhost:port.
A8. TTL=1,2,3… each zeroing router returns Time Exceeded; * * * = filtered/rate-limited ICMP, not failure.
A9. hops ≈ sending TTL (64 or 128) − received TTL (e.g. 64−57 = 7).
A10. Data arrived but the application hasn't read it — slow/hung app, or nowhere reading at all.
A11. Capture filters (tcpdump/BPF) limit what's recorded pre-capture; display filters (Wireshark) slice post-capture.
A12. At hop 4 — the jump appears crossing INTO hop 4 (its incoming link), since hop 3 responded quickly.
A13–A16. Ladder + checklist, state stories from §5, the four commands from §6, and PMTUD: blocked "Fragmentation Needed" ICMP = sender never learns to shrink packets.
Wrap-Up — carry these into Lecture 13
The ladder
Debug bottom-up: ip addr → ping GW → ping 8.8.8.8 → dig → curl/port. Each rung isolates one layer's failure.
States tell stories
SYN_SENT = no reply; CLOSE_WAIT = you forgot close(); TIME_WAIT = normal 2×MSL cool-down, not a leak.
Capture smart
tcpdump -n (no lookups) to record; Wireshark display filters to analyse. BPF limits what's captured, filters slice what's shown.
Silent failures
Blocked ICMP = PMTUD death: big uploads hang, small ones pass. traceroute's * * * = filtered ICMP, not always a failure.
